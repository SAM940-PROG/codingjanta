Binary Search

Find anything in a sorted space — or find the smallest answer that passes a yes/no test — by throwing away half the candidates at every step.

LevelFoundation → Core
PrerequisitesArrays · Big-O · sorted data

ProgressionWarm-up → Easy → Medium → Hard

If you're rusty, that's normal

You haven't lost the ability to learn this — you've lost recognition, which is exactly what a break does to rarely used patterns. This lesson rebuilds recognition first ("when do I reach for this?"), then the implementation habit. If syntax feels fuzzy, read the code slowly; the reasoning comments carry the weight, not memorized APIs.

Plain-language intuition

Suppose you must find a value among a million sorted items. Checking each one is a million checks. But sorted order is a promise: if the middle item is too small, everything left of it is also too small, so you can discard the whole left half sight unseen. Repeat on the remaining half. Each check halves the suspects, so a million items take about 20 checks.

Analogy: finding a word in a paper dictionary. You don't read page 1, then page 2. You open near the middle, see whether your word comes before or after, and discard the useless half. Binary search is that habit, formalized.

When should I think “Binary Search”?

Recognition beats memorization. When you read a problem and see one of these shapes, let Binary Search come to mind — then verify the monotonic property before coding.
SignalWhy it points to Binary Search
Sorted array + “find a value / position”Order lets one comparison eliminate a whole half.
Sorted data + “first / last occurrence”Duplicates form a block; lower/upper bound finds its edges in O(log n).
“Minimum possible X” / “maximum possible X”Classic search on answer: the answer lives in a range, not an array.
A monotonic yes/no condition (FFFF…TTTT)Monotonicity is the real requirement — sorted arrays are just one instance.
The answer can be checked independentlyIf check(X) is easy (usually O(n)), Binary Search finds the boundary fast.
Red flags — probably NOT Binary Search:
  • Unsorted data with no monotonic predicate to exploit.
  • You need ALL matches counted in a way bounds can't frame.
  • The predicate isn't monotonic (true…false…true) — verify before coding.

Brute force first — why we need this at all

  1. Problem. Given a sorted array of n numbers, is target present?
  2. Brute-force idea. Scan left to right and compare each element. Simple, correct, works on any array.
  3. Complexity. Time O(n), space O(1).
  4. Why it becomes too slow. At n = 10⁶ with many queries (typical in contests: q up to 10⁵), O(n·q) means ~10¹¹ operations — seconds turn into hours. Sorted order is unused information.
  5. The Binary Search insight. Sorted order makes the predicate “a[i] < target” monotonic: once it flips, it never flips back. So one middle comparison tells you which half cannot contain the answer — discard it.

Never treat Binary Search as magic: it is linear scan plus the exploitation of order.

One fully worked problem

Problem: Koko Eating Bananas — LeetCode 875LeetCode (representative “minimum possible X” problem; the same shape appears constantly on Codeforces under different stories).

  1. What is being asked? Piles of bananas; Koko eats at speed k piles-per-hour equivalent (k bananas/hour, one pile at a time, round up partial hours). Given guard return time h hours, find the smallest integer speed that finishes everything in time. We minimize k, plain language: “how slow can she afford to be?”
  2. What do the constraints imply? n ≤ 10⁴, pile size and h up to 10⁹. Trying every speed up to max pile (10⁹) with an O(n) check each is up to ~10¹³ work — impossible. But an O(n log maxPile) solution (≈ 10⁴ × 30) is trivial. Constraints scream “log factor available.”
  3. Brute force. Try k = 1, 2, 3, …; for each, compute hours = Σ ceil(pile / k); return the first k with hours ≤ h.
  4. Why brute force is too slow. O(maxPile × n): up to ~10⁹ × 10⁴. The check is correct but the outer scan wastes the structure of the problem.
  5. The key observation. canFinish(k) is monotonic: if speed k finishes in time, every faster speed also finishes (FFFF…TTTT over k). So the speeds form exactly the shape Binary Search needs — even though there is no sorted array.
  6. The algorithm. Search the answer range [1, maxPile]. Mid m: if canFinish(m), the answer is m or slower-left → hi = m; else we need faster → lo = m + 1. Loop while lo < hi; return lo.
  7. Dry run. piles = [3,6,7,11], h = 8. maxPile = 11 → range [1,11]. mid 6: hours = 1+1+2+2 = 6 ≤ 8 → hi = 6. mid 3: hours = 1+2+3+4 = 10 > 8 → lo = 4. mid 5: hours = 1+2+2+3 = 8 ≤ 8 → hi = 5. mid 4: hours = 1+2+2+3 = 8 ≤ 8 → hi = 4. lo == hi == 4 → answer 4. ✓
  8. Implementation. See the annotated code below (jump to code).
  9. Complexity. Time O(n log maxPile), space O(1).

Annotated implementation

Two listings: the classic search (learn the invariant here), then the worked-problem solution (same invariant, applied to answers).

Listing 1 — Classic binary search (memorize this shape)

public int binarySearch(int[] a, int target) {
    int lo = 0, hi = a.length - 1;
    // INVARIANT: if target exists, it is inside [lo, hi].
    while (lo <= hi) {
        // Overflow-safe mid: (lo + hi) can overflow for large indices.
        int mid = lo + (hi - lo) / 2;
        if (a[mid] == target) return mid;
        // a[mid] < target + sorted order proves EVERYTHING at
        // indices <= mid is too small — discard the whole left half.
        if (a[mid] < target) lo = mid + 1;
        // Symmetric: a[mid] proves everything >= mid's right side
        // only; discard mid and everything right of it.
        else hi = mid - 1;
    }
    // Range is empty, so target was proven absent — not "not found yet".
    return -1;
}

Listing 2 — Worked solution: Koko (binary search on answer)

public int minEatingSpeed(int[] piles, int h) {
    int lo = 1, hi = maxOf(piles);
    // INVARIANT: the answer is always inside [lo, hi].
    // check(m) is monotonic: false...false true...true.
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        // mid might BE the answer, so keep it: hi = mid (not mid - 1).
        if (canFinish(piles, h, mid)) hi = mid;
        // mid is proven too slow; everything <= mid is too slow too.
        else lo = mid + 1;
    }
    return lo;
}

// Decision procedure: easy O(n) check that BS calls O(log M) times.
// Hours can exceed int range (n * pile up to ~1e13), so accumulate in long.
private boolean canFinish(int[] piles, int h, int speed) {
    long hours = 0;
    for (int p : piles) hours += (p + (long) speed - 1) / speed; // ceil without doubles
    return hours <= h;
}
Complexity (this lesson's code). Listing 1 — Time: O(log n), Space: O(1). Listing 2 — Time: O(n log maxPile), Space: O(1). Each step removes roughly half of the remaining candidates, so the number of checks grows logarithmically, not linearly.

Common Binary-Search-specific mistakes

MistakeWhy it happens / how to avoid
mid = (lo + hi) / 2 overflowlo + hi can overflow int near 2³¹. Always use lo + (hi - lo) / 2.
Wrong loop condition (< vs <=)lo <= hi pairs with hi = len − 1; lo < hi pairs with hi = len or answer-search. Mixing them skips the last candidate or loops forever.
Infinite loop on two elementsUpdating with lo = mid / hi = mid without progress stalls when hi − lo == 1. Use mid + 1 / mid − 1, or the hi = mid / lo = mid + 1 answer-search pair.
Mixing inclusive/exclusive rangesPick one convention per function and keep it: either [lo, hi] inclusive or [lo, hi) half-open. The reference templates below show both — don't blend them mid-function.
Returning mid too early in bound searchesLower/upper bound asks for the first position satisfying a condition; returning on first match gives a match. Shrink the range instead and return lo.
Duplicates handled by luckClassic search returns any occurrence. If the problem wants first/last, you must use the lower/upper-bound template, not hope.
Broken invariant (“searching” an unsorted/monotonic-violating space)Discarding a half is only legal if the predicate is monotonic. Rotated arrays, bitonic arrays, or buggy check() functions silently break the proof — verify monotonicity first.

🌱 Warm-up problems

Do these before serious practice. Original, platform-neutral, increasing in demand: recognition → implementation → small application. No fake problem IDs.

  1. Exists? — Given a sorted array and a target, return true/false.
    Solution

    Classic template; return mid on equality, -1/false when the range empties. Time O(log n).

    Concept: recognition + classic template. Difficulty: trivial.
    Hint (optional)Sort order means one middle comparison eliminates a half. Start from Listing 1.
  2. First occurrence. — Sorted array may contain duplicates; return the index of the first target, or −1.
    Solution

    Lower bound: on match set hi = mid (never return early); loop lo < hi; verify a[lo]==target at the end.

    Concept: lower bound. Difficulty: easy.
    Hint (optional)Don't return on match — record nothing, just move hi = mid and let the loop converge on the left edge.
  3. Insert position. — Sorted array + target; return the index where it belongs to keep order.
    Solution

    Lower bound again — return lo unconditionally; absence just means insertion point.

    Concept: lower bound as insertion point. Difficulty: easy.
    Hint (optional)This is exactly what lower bound returns even when the target is absent — return lo, not −1.

1. What does Binary Search require?

Explanation

Discarding half the space is only legal if “too small / too big” generalizes — that is monotonicity. Sorted arrays are the common special case.

2. O(log n) for n = 1,000,000 means roughly…

Explanation

2²⁰ ≈ 10⁶. Halving 20 times collapses a million candidates to one.

3. If a[mid] < target in a sorted array, you…

Explanation

Sortedness proves all of those are too small — not just mid.

4. For “first true” answer-search over [lo, hi], the correct pair is…

Explanation

Mid may be the answer, so it must stay in range (hi = mid). The lo < hi loop converges exactly on the boundary.

5. Which problem is most likely Binary Search on answer?

Explanation

“Minimum feasible X” with an easy feasibility check is the canonical search-on-answer shape (Koko, Ship Packages, Split Array).

Quick reference

Core templates + why they matter (reference) “Why?” 
// Template 1: Classic — find exact target
public int binarySearch(int[] arr, int target) {
    int lo = 0, hi = arr.length - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;   // Avoid overflow!
        if (arr[mid] == target) return mid;
        else if (arr[mid] < target) lo = mid + 1;
        else hi = mid - 1;
    }
    return -1;  // Not found
}

// Template 2: Lower Bound — first index where arr[i] >= target
public int lowerBound(int[] arr, int target) {
    int lo = 0, hi = arr.length;  // NOTE: hi = length (not length-1)
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (arr[mid] < target) lo = mid + 1;
        else hi = mid;
    }
    return lo;  // First position >= target
}

// Template 3: Upper Bound — first index where arr[i] > target
public int upperBound(int[] arr, int target) {
    int lo = 0, hi = arr.length;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (arr[mid] <= target) lo = mid + 1;
        else hi = mid;
    }
    return lo;  // First position > target
}

// Template 4: Binary Search on Answer
// "What is the minimum/maximum value X such that condition(X) is true?"
public int binarySearchOnAnswer(int lo, int hi) {
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (check(mid)) hi = mid;     // mid might be answer, search left
        else lo = mid + 1;            // mid too small, search right
    }
    return lo;
}

// Template 5: Binary Search on Real Numbers (floating point)
public double binarySearchDouble(double lo, double hi) {
    for (int iter = 0; iter < 100; iter++) {  // 100 iterations ≈ 10^-30 precision
        double mid = (lo + hi) / 2;
        if (check(mid)) hi = mid;
        else lo = mid;
    }
    return lo;
}

Why it matters: Binary search reduces O(n) to O(log n). It works not just on sorted arrays — any scenario with a monotonic predicate (false, false, …, true, true, …) can use binary search. “Binary Search on Answer” is a meta-technique used in hundreds of competitive programming problems.

When to reach for it: Use binary search when the answer space is ordered and checking one side lets you eliminate the other half. It turns a slow linear scan into a very fast logarithmic search — essential for problems with large constraints (n ≤ 10⁶+). Also used in “binary search on answer” problems where you search for the minimum/maximum value that satisfies a condition.

What to learn next
